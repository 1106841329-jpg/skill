## 产品环节及证据边界

这是一组业务环节，不代表所有环节已经自动串通。

| 环节 | 证据状态 | 解释时的边界 |
|---|---|---|
| 图纸进入拆单助手，生成工序、报价或质检相关结果 | 9月3日实测与学习记录已描述相关入口和输出 | 不能据此认定全部格式、图纸及客户场景可用 |
| 人工查看、审核与修改 | 历史实测已记录相关操作；正式工艺及商务、质量判断仍需客户确认 | 生成结果与正式报价、生产或质量放行不是同一件事 |
| 拆单结果进入小工单 | 9月3日记录称已验证前半段连接 | 具体字段、触发方式、权限、重复写入及异常处理须按版本核对，不能概括为全自动 |
| 小工单承接工单、工序任务、报工和进度记录 | 已有产品学习与实操记录 | 数据完整及时仍依赖实际操作，不代表现场所有事件已记录 |
| 人工修改成为后续记忆或案例 | 既有资料有相关讨论，具体机制及效果待确认 | 不能由存在“记忆”概念推导每次修改都会被保存、检索或有效采用 |
| 生产实际工时、成本及质量结果自动回到工厂记忆 | 尚无充分证据 | 明确标注待确认，不画成已实现的自动回流箭头 |

历史边界：9月3日至4日整理认为报价优先适配机加工零件，数量参与成本计算；钣金覆盖及装配、焊接总成能力有限；质检模块当时仍在早期。只将这些用作需核对的历史背景，不认定今天仍完全相同。

面向按图生产、非标、多品种小批量客户时，可帮助用户理解图纸到工艺、工时、报价、质检的工作。每次演示选择什么入口，应依据具体客户的真实流程及当前产品能力。

## 技术词怎样连接业务

以下均为候选映射或解释线索，不是CAD Agent源码架构的断言。

| 主题 | 理解线索 | 有用的确认点 |
|---|---|---|
| Context | 本次处理可用的图纸、工厂配置、要求或案例等信息 | 哪些信息实际传入？图纸之外哪些是必需、哪些只是改善适配？ |
| 快照、版本、权威数据源 | 保存或读取的是哪个时间点的数据 | 修改是否保存，后续计算读取哪一版？ |
| API、同步与异步 | 数据交换、任务何时返回及何时完成 | 返回成功代表已接收还是已完成？失败如何呈现？ |
| 缓存 | 为复用或加速保留的信息 | 什么情况下失效，是否可能读到旧结果？ |
| 重置、回滚 | 对状态、配置或版本的不同处理 | 实际影响哪些数据？是临时处理还是正式修复？ |
| 日志、复现、环境 | 还原问题的操作、版本和时间 | 能否在同一环境复现？客户环境是否已有修复？ |
| 指标、置信度 | 测量或评分的对象和口径 | 测的是字段、工序还是整份结果？评分经过什么验证？ |
| Agent、模型与工具 | 多步任务如何组织与执行 | 哪一步生成、哪一步调用工具、哪一步需人工确认？ |

例如历史现场曾讨论“修改工序后重新报价未采用新工序”。这只能说明观察到了特定行为，不能直接认定根因是缓存或快照，更不能把重置视为已修复。确认保存、读取和版本关系后，才能判断原因与影响。

技术方案是否有价值，应连接具体后果：等待或失败是否阻碍试用完成，修改成本是否影响持续采用，配置和集成是否妨碍复制交付。技术先进性本身不能证明客户愿意付费。

## 按问题选择证据

- 查“实际发生什么”：使用相应客户环境、版本、时间和复现记录。一次测试只支持该测试范围。
- 查“系统如何实现”：结合代码、配置和开发说明，并确认是否部署到目标环境。
- 查“团队决定什么”：以明确负责人决策或正式记录为据；路线图只支持计划层面的结论。
- 查“客户感受和业务结果”：回到客户原话、操作记录和业务数据，不能由内部设计代替。
- 总结和推断用于建立候选解释，涉及动态状态时回到原始来源；无法读取则明确缺口。
